# Factory Improvement Proposals and Evaluation (`factory.improvement`) — Issue #68

`factory.improvement` implements Slice `#68` (Part A of `#32`, `[Factory 16a] Retain and compare bounded factory-improvement proposals`): an explicitly invoked, bounded workflow that turns an observed failure into a structured skill, tool, or check proposal, evaluates baseline and candidate against identical named cases and a pinned rubric under isolated conditions, and produces a reviewable report.

## Invocations

```bash
# 1. Create and validate a canonical proposal
python3 -m factory.improvement create-proposal \
  --out <proposal.json> \
  --from-file <draft_proposal.json>

# 2. Evaluate baseline vs candidate
python3 -m factory.improvement evaluate \
  --proposal <proposal.json> \
  --evidence-dir <evidence_dir> \
  --repo <product_or_test_repo> \
  --json
```

## Contract for #69 Review and Governance

`#69` consumes the evaluation report generated by `#68` to assemble an issue/PR review packet for human maintainer review.

### Report Fields

- `schema_version`: Must equal `1`.
- `proposal_digest`: SHA-256 digest of canonical proposal JSON text.
- `factory_revision`: Git revision of the factory consumed during evaluation.
- `candidate_content_digest`: SHA-256 digest of the proposed candidate content file.
- `baseline_identity`: Immutable baseline commit SHA or identifier.
- `candidate_identity`: Immutable candidate identifier.
- `proposal`: Complete bound proposal definition.
- `execution_conditions`: Pinned conditions (`time_limit_seconds`, `allow_network: false`, `env_sanitized: true`, `permitted_substitution`).
- `baseline_results`: Case-by-case execution outcomes and rubric grading for baseline.
- `candidate_results`: Case-by-case execution outcomes and rubric grading for candidate.
- `comparison`: Summary of behavioral rule verification:
  - `rule`: `"baseline-failed-candidate-passed"`
  - `rule_satisfied`: `true` when baseline behavioral failure and candidate success are demonstrated and all candidate regressions pass.
  - `baseline_demonstrated_failure`: `true` when baseline executed without timeout/launch error and failed rubric.
  - `candidate_demonstrated_success`: `true` when candidate executed and passed all improvement cases.
  - `candidate_regressions_passed`: `true` when all required regressions executed and passed on candidate.
  - `reasons`: List of failure reasons if ineligible.
- `measurements`: Duration, token usage, and cost with provenance (`reported`, `estimated`, `unavailable`). Missing usage/pricing remains `null`/`unavailable`, never inferred zero.
- `eligibility`: `"improvement-eligible"` or `"ineligible"`.
- `authority_note`: Fixed literal: `"improvement-eligible only; not approved, installed, merged, or parent-accepted"`.

### Validation Rules for #69

1. Reject reports where `schema_version != 1` or `authority_note` differs from the literal value.
2. Re-hash the proposal JSON and ensure it matches `proposal_digest`.
3. Verify `candidate_content_digest` matches the SHA-256 of candidate content.
4. Verify `eligibility == "improvement-eligible"` and `comparison.rule_satisfied is true`.
5. Require non-empty regressions and confirm all candidate regressions passed.
6. Confirm baseline exhibited actual behavioral failure under the rubric (not launch failure, timeout, or missing executable).

### Authority and Trust Boundary

- **Eligibility is not approval**: An `"improvement-eligible"` report demonstrates behavioral improvement under test rubrics only.
- It grants **NO authority** to install files, mutate delivery prompts, modify protected policies, or promote lessons.
- Only a human maintainer's review through the repository's issue/PR review workflow and explicit merge to `main` can approve or promote factory policy or durable lessons.
