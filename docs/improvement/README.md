# Factory Improvement Proposals and Evaluation (`factory.improvement`) — Issue #68

`factory.improvement` implements Slice `#68` (Part A of `#32`, `[Factory 16a] Retain and compare bounded factory-improvement proposals`): an explicitly invoked, bounded workflow that turns an observed failure into a structured skill, tool, or check proposal, evaluates baseline and candidate against identical named cases and a pinned rubric under isolated conditions, and produces a reviewable report.

## Invocations

```bash
# 1. Create and validate a canonical proposal
python3 -m factory.improvement create-proposal \
  --out <proposal.json> \
  --from-file <draft_proposal.json>

# 2. Evaluate baseline vs candidate
python3 -m factory.improvement evaluate \
  --proposal <proposal.json> \
  --evidence-dir <evidence_dir> \
  --repo <product_or_test_repo> \
  --json
```

## Contract for #69 Review and Governance

`#69` consumes the evaluation report generated by `#68` to assemble an issue/PR review packet for human maintainer review.

### Explicit Case Input Contract

Cases may declare retained input files staged into the isolated worktree before execution:
`{"path": "<external-source>", "target_path": "<relative-worktree-destination>", "sha256": "<digest>"}`
- `path`: External source file path (canonicalized to absolute on draft import). It does not default to `target_path`.
- `target_path`: Explicit worktree-relative destination path. Must be a safe relative path without component escapes.
- `sha256`: SHA-256 digest of input file bytes, verified at validation and staging.
Identical verified bytes are staged at `target_path` for both baseline and candidate before case execution. Input destinations must not collide with other inputs or overlap with `proposed_change.target_path`.


### Report Fields

- `schema_version`: Must equal `1`.
- `proposal_digest`: SHA-256 digest of canonical proposal JSON text.
- `factory_revision`: Git revision of the factory consumed during evaluation.
- `candidate_content_digest`: SHA-256 digest of the proposed candidate content file.
- `baseline_identity`: Immutable baseline commit SHA or identifier.
- `candidate_identity`: Immutable candidate identifier.
- `proposal`: Complete bound proposal definition.
- `execution_conditions`: Pinned conditions (`time_limit_seconds`, `allow_network: false`, `env_sanitized: true`, `permitted_substitution`).
- `baseline_results`: Case-by-case execution outcomes and rubric grading for baseline.
- `candidate_results`: Case-by-case execution outcomes and rubric grading for candidate.
- `comparison`: Summary of behavioral rule verification:
  - `rule`: `"baseline-failed-candidate-passed"`
  - `rule_satisfied`: `true` when baseline behavioral failure and candidate success are demonstrated and all candidate regressions pass.
  - `baseline_demonstrated_failure`: `true` when baseline executed without timeout/launch error and failed rubric.
  - `candidate_demonstrated_success`: `true` when candidate executed and passed all improvement cases.
  - `candidate_regressions_passed`: `true` when all required regressions executed and passed on candidate.
  - `reasons`: List of failure reasons if ineligible.
- `measurements`: Duration, token usage, and cost with provenance (`reported`, `estimated`, `unavailable`). Missing usage/pricing remains `null`/`unavailable`, never inferred zero.
- `eligibility`: `"improvement-eligible"` or `"ineligible"`.
- `authority_note`: Fixed literal: `"improvement-eligible only; not approved, installed, merged, or parent-accepted"`.

### Validation Rules for #69

1. Reject reports where `schema_version != 1` or `authority_note` differs from the literal value.
2. Require a structurally valid embedded proposal and verify `proposal_digest` matches its canonical SHA-256 digest (and matches external `proposal_json` if supplied).
3. Verify `candidate_content_digest` matches the bound proposal's candidate content hash (`proposed_change.content_sha256` and `candidate.content_sha256`).
4. Accept only documented eligibility states: `"improvement-eligible"` and `"ineligible"`. Valid ineligible reports remain accepted reviewable records, not approvals.
5. For both sides (`baseline_results` and `candidate_results`), verify complete, matching named-case and rubric evidence corresponding to the bound proposal cases.
6. Require non-empty regressions and verify that all candidate regressions executed and passed without launch failure or timeout.
7. For eligible reports, verify that baseline exhibited actual behavioral failure under the rubric (not launch failure, timeout, execution error, or unexecutable command) on all improvement cases, and candidate demonstrated rubric success on all improvement cases.
8. Verify summary comparison flags match raw case outcomes; reject truthy flags that contradict recorded results.
9. Retained reports validate without requiring the original external draft or candidate files on disk.

### Authority and Trust Boundary

- **Eligibility is not approval**: An `"improvement-eligible"` report demonstrates behavioral improvement under test rubrics only.
- It grants **NO authority** to install files, mutate delivery prompts, modify protected policies, or promote lessons.
- Only a human maintainer's review through the repository's issue/PR review workflow and explicit merge to `main` can approve or promote factory policy or durable lessons.

## Promotion Gate and Exact-Version Resolver (`factory.promotion`) — Issue #69

`#69` implements the human-maintainer promotion gate and exact-version resolver (Part B of `#32`).

### Review Packet Generation

Turns an improvement-eligible report into an issue/PR review packet without autonomous submission or promotion side effects:

```bash
python3 -m factory.improvement build-review-packet \
  --report <report.json> \
  --out <packet.json>
```

- Packet includes proposal digest, candidate content digest, factory revision, bounded proposed change, failure evidence, expected improvement, complete comparison with regressions, and measurement provenance.
- Fixed authority note: `"review-packet-only; not approved, submitted, merged, or promoted"`.
- Validates eligibility directly from recorded case results; rejects ineligible or tampered reports.

### Authoritative Resolver Contract for #70

`resolve_approved_version` enforces exact approved version selection:

- **Trust Anchor**: Maintainer-merged Pull Request targeting `main` (`merged: true`, `state: "closed"`), with `merge_commit_sha` verified as an ancestor of `main`.
- **Untrusted Inputs**: Candidate-local `approved` flags, delivery-approval records (`#58`), unmerged branches, caller-supplied refs, and dirty workspace files are rejected.
- **Fail-Closed Verification**: Rejects unapproved, unmerged, altered proposal content, altered candidate bytes, or altered evaluation evidence.
- **Exact Git Retrieval**: Extracts candidate bytes directly from git object storage (`git show {merge_commit_sha}:{target_path}`); never reads local workspace files.
- **Distinct Storage Contract**:
  - Shared policy paths: `factory/`, `skills/`, `bin/`, `guards/`.
  - Durable lessons path: `factory/lessons/`.
  - Strictly excluded: `pilot/`, `examples/`, `tests/`, `evidence/`, `attempts/`, `homes/`, `context/`.
- **Refusal Codes**: `"untrusted-approval-source"`, `"unmerged-revision"`, `"unintended-target"`, `"ineligible-proposal"`, `"binding-mismatch"`, `"mismatched-approved-content"`, `"missing-approved-content"`, `"forbidden-storage-path"`.
- **No Delivery Activation**: Selection does not mutate delivery configs, install files, or activate candidate lessons in delivery runs.

## Approved Factory Policy Delivery Consumption (`factory.deliver`) — Issue #70

`factory.deliver` implements Slice `#70` (Part C of `#32`, `[Factory 16c] Consume only approved factory versions in optional delivery improvement workflows`): an explicit, bounded per-run integration that consumes verified immutable policy content at the delivery boundary and records honest provenance.

### Invocations

```bash
# 1. Ordinary delivery (baseline preserved, no improvement policy selected)
python3 -m factory --repo <repo> --home <home> deliver --task <gid>

# 2. Delivery with explicitly selected approved policy
python3 -m factory --repo <repo> --home <home> deliver \
  --task <gid> \
  --policy-report <report.json> \
  --policy-proof <proof.json> \
  --policy-proposal <proposal.json>

# Or using a selection descriptor:
python3 -m factory --repo <repo> --home <home> deliver \
  --task <gid> \
  --policy-selection <selection.json>
```

### Consumption Boundary & Supported Mechanisms

- **Lessons (`factory/lessons/`)**: Immutable approved bytes are retained under `consumed-policy/` and provided to the builder prompt under an explicit `Approved factory lessons:` section.
- **Skills (`skills/`)**: Retained in `consumed-policy/` and staged into the isolated worker home at `.gemini/antigravity-cli/skills/`.
- **Tools (`bin/`, `factory/`)**: Retained in `consumed-policy/`, staged with executable permissions into the isolated home `bin/`, and prepended to the worker `PATH`.
- **Checks (`guards/`, `factory/`)**: Retained in `consumed-policy/` and executed directly against the candidate worktree; failing checks block delivery with `approved-policy-check-failed`.

### Truth & Provenance Boundaries

- **Ordinary Delivery Baseline**: Deliveries without explicit policy selection record `selected: false, status: "none"`, preserving baseline checks and never scanning proposal directories or product context.
- **No Activation Side Effects**: Creating or evaluating a proposal never activates it; unapproved lessons remain excluded from subsequent deliveries.
- **Immutable Git Content & Drift Detection**: Delivery consumes exact git object bytes (`git show {merge_commit_sha}:{target_path}`); local workspace files are never labeled as approved revisions when they differ (`local_source_drift: true`).
- **Resume Compatibility**: Re-running or resuming delivery on an existing attempt validates policy selection identity, retained artifact existence and digest, and factory revision before reusing prior candidate/approval evidence.
- **Preserved Identity**: Resolved policy consumption provenance survives through QA, repairs, security review, and record rewrites.
